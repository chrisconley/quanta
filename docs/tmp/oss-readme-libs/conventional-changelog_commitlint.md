# Analysis: conventional-changelog/commitlint

- **Repo**: conventional-changelog/commitlint (~17.5k stars)
- **Type**: Node.js CLI + shareable-config monorepo that lints commit messages against Conventional Commits and related rulesets.
- **Length**: ~7 KB. Medium-short; heavy on lists, light on prose.

## Sections

1. **Linkbar header** — an H1 that is actually two links: "[Get Started](https://commitlint.js.org/guides/getting-started) | [Website](https://commitlint.js.org)". The repo name never appears as an H1.
2. **Blockquote tagline** — "> Lint commit messages".
3. **Centered animated SVG demo** — `docs/public/assets/commitlint.svg`, a terminal recording generated by `svg-term-cli`. The README includes the exact reproduction command as a blockquote (`cat docs/assets/commitlint.json | svg-term --out ...`) below the image.
4. **Badge row** — three badges (npm latest, Node compatibility, GitHub Actions) via link-reference footnotes (`[2]`/`[3]`/`[13]`/`[14]`/etc.).
5. **Three-bullet emoji manifesto** — "🚓 Be a good `commitizen` / 📦 Share configuration via `npm` / 🤖 Tap into `conventional-changelog`".
6. **Contents** — a full auto-generated-looking TOC (double-indented because the site title header `[Get Started | Website]` became the root), 18 entries.
7. **What is commitlint** — one-sentence definition, then three labeled code blocks (an abstract `type(scope?): subject` with a note on multiple scope delimiters `"/", "\" and ","`, plus three "Real world examples" tagged `text`: `chore: run tests on travis ci`, `fix(server): send cors headers`, `feat(blog): add comment section`). Closes with an 11-item bullet list of common types (build/chore/ci/docs/feat/fix/perf/refactor/revert/style/test).
8. **Benefits of using commitlint** — two external links: the Conventional Commits "Why" page and a slides.com deck "The perks of committing with conventions".
9. **Getting started** — two bullets, Local setup vs CI setup, both linking to `commitlint.js.org/guides`.
10. **CLI** — three bullets (purpose, install one-liner, monorepo package path `./@commitlint/cli`).
11. **Config** — a 15-item exhaustive list of recognized config filenames (`.commitlintrc`, `.commitlintrc.{json,yaml,yml,js,cjs,mjs,ts,cts,mts}`, `commitlint.config.{js,cjs,mjs,ts,cts,mts}`, plus `commitlint` field in `package.json` and in pnpm's `package.yaml`).
12. **Important note about Node 24+** — a mini-troubleshooting callout about ESM module loading breaking `commitlint.config.js` in projects without a `package.json`, with two fixes (`npm init es6` or rename to `.mjs`).
13. **Shared configuration** — eight-entry list of config packages (six first-party `@commitlint/config-*` and two third-party `conventional-changelog-lint-config-*`) with a `⚠️` blockquote warning about the naming convention required for publishing your own shareable config.
14. **Documentation / API / Tools / Roadmap / Version Support and Releases / Releases / Related projects / License / Development** — mostly one-to-four-bullet sections; a versioned-release table (v19 02/2024, v18 10/2023), an explicit "EOL is usually after around a year" note, and a blunt "We're not a sponsored OSS project" statement inviting PRs for older-version security patches.
15. **Install and run** — six-line `git clone` + `yarn`/`yarn run build`/`yarn start`/`yarn run commitlint` recipe.
16. **Link-reference footer** — numbered link definitions `[0]` through `[14]` (with gaps: 6, 7, 11, 12 are missing), including orphaned "stability-experimental" and `@commitlint/cli/next` badges that aren't used in the rendered document.

## Tone & style

- **Register**: Documentation-index — the README mostly enumerates (config filenames, shared configs, package names, release dates) rather than persuades. A single editorial-sentence voice occasionally surfaces ("We're not a sponsored OSS project").
- **Voice**: Third-person descriptive for definitions ("commitlint checks if your commit messages..."); first-person plural only in the release-policy candor ("we can't promise," "we're happy if you can provide a PR").
- **Formatting**: Link-reference-style badges (numbered footnotes), HTML `<p align="center">` only for the SVG hero, emoji-prefixed manifesto, no sub-headings within most list sections, link-reference bibliography at the end.

## Notable conventions

- **H1 is a linkbar, not a project name** — the rendered page never says "commitlint" at the top; it says "Get Started | Website," making the README function as a landing-page table of contents for the real docs site. The `## Contents` entry even self-references this anomaly as `[Get Started | Website](#get-started--website)`.
- **SVG terminal demo with its own reproduction command embedded** — the README teaches you how the hero image was generated (`svg-term-cli` pipeline with Seti profile) right below the image, blurring the line between demo and tooling manifest.
- **Exhaustive file-name enumeration (15 recognized config paths)** — rather than documenting "cosmiconfig-style lookup," the README lists every filename commitlint resolves, which is both exhaustive and brittle (new extensions must be added here and in code simultaneously).
- **"Important note about Node 24+" as a first-class README section** — a troubleshooting entry for an ESM-loader regression gets its own H3 under Config, unusual for a README; reflects how painful and common the failure mode was at the time of writing.
- **Shareable-config naming discipline in a blockquote warning** — "make sure it has a name aligning with the pattern `commitlint-config-emoji-log` or `commitlint-config-your-config-name`" — a convention propagated purely by this README (and the resolver code), with emoji-log as the concrete example.
- **Release-support table plus candid "We're not a sponsored OSS project"** — the version matrix (v19/v18, ~1-year EOL) and the admission that backports depend on community PRs is unusually forthright and is essentially a liability disclaimer.
- **Orphaned link references in the footer** (`[0]`/`[1]` stability-stable, `[8]`/`[9]` stability-experimental, `[10]` `@commitlint/cli/next`) — badges and numbered definitions remain in the link-reference dictionary even after the corresponding inline references were removed, betraying long-lived incremental edits.

## Takeaway pattern

This is the "monorepo index page" README: the primary product is the hosted docs site, and the README's job is to enumerate config file names, package paths, shared-config bundles, and release-policy facts in a scannable reference format. Lesson: tooling projects whose surface area is configuration (not API) end up with READMEs that are mostly lists of filenames and package names — and the interesting prose is compressed into single sentences ("We're not a sponsored OSS project," "EOL is usually after around a year") that communicate scope of responsibility. The linkbar-as-H1 and SVG-with-reproduction-command are small self-aware touches that signal a mature project comfortable pointing readers away from the repo to the real docs, while still using the README as its own changelog of operational edge cases (Node 24+, pnpm's `package.yaml`, the shareable-config naming prefix).
